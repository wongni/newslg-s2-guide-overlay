# 전법 데이터 완전 자동 추출 — 구현 플랜

> 목표: **모든 무장의 고유 전법 + 일반 전법** 이름·설명·수치를 자동으로 매핑하여 `kb/`에
> 무장/전법 이름이 들어간 개별 파일로 정리한다.
>
> 대상 게임: 삼국지: 천하결전 (com.bhk.newslgkr, Unity 2022.3 + IL2CPP, 에셋/메타데이터 자체 암호화)
> 접근 원칙: **읽기 전용(PROCESS_VM_READ)**, 코드 주입·쓰기·후킹 없음. 개인 참고용.

---

## 현재 상태 / 문제 정의

- 현재 스크립트(`tools/mem_extract.py`, `scripts/mem_extract.py`)는 메모리에서 **한글 평문 문자열만** 긁어 정렬·중복제거한다.
- 결과: 전법 **이름 테이블**과 **설명 테이블**이 물리적으로 분리 저장 + 정렬로 인접성 소실 → **이름↔설명 연결 정보가 없음**.
- 지금까지는 "효과 문구로 수동 검색 → 이름 대조"(반자동)로 개별 확인. 전 전법 자동화 불가.

### 핵심 아이디어 (자동 매핑)
게임 UI는 런타임에 `전법ID`로 이름·설명·메타를 조회한다. 따라서 **한글 문자열이 아니라 문자열을 참조하는 구조(포인터/ID 테이블)를 메모리에서 복원**하면 `이름 ↔ 설명 ↔ 수치 ↔ 무장`을 ID 기준으로 묶을 수 있다.

관측된 단서(이미 추출된 덤프에서 확인됨):
- 전투 로그에 `insSkill_20140_...`, `insSkill_200101_...`, `insSkill_20660_...` 같은 **전법 ID 토큰**이 존재. (예: 칠군수몰=20140, 화하 진압=200101, 기민한 전술=20660)
- 무장 링크 토큰 `320176908673_2001`(관우), `_2012`(조운) 등 **무장 인스턴스/전법 슬롯 ID** 패턴 존재.
- 설명 문자열의 수치는 `$base+giver.skillLv*step$` 형식(만렙=Lv10).

→ 이 ID들이 **문자열 포인터와 함께 배열/구조체로 메모리에 존재**할 가능성이 높다. 이를 파싱하는 것이 "정확한 방법".

## 접근 방식 3안 (난이도/정확도 순)

### 방안 A — 문자열 포인터 역참조 스캐닝 (권장, 순수 읽기 전용)
IL2CPP는 C# `string`을 **`System.String` 객체**(길이 + UTF-16 본문)로 힙에 둔다. 로컬라이제이션/전법 테이블은 **string 객체 포인터의 배열** 또는 **(id, namePtr, descPtr) 구조체 배열**로 존재한다.

절차:
1. 메모리 전체에서 목표 한글 문자열(이름·설명)의 **주소**를 수집(문자열→주소 인덱스).
2. 각 문자열의 **관리 객체 헤더 주소**(본문 앞 오프셋) 후보를 계산.
3. 메모리에서 **그 주소값(포인터)을 담고 있는 8바이트 슬롯**을 역스캔 → 포인터가 인접해 모여있는 배열(=테이블) 발견.
4. 같은 구조체/레코드 안에서 **이름 포인터와 설명 포인터가 고정 오프셋으로 함께** 나타나는 패턴을 찾는다 → 이름↔설명 쌍 확정.
5. 같은 레코드의 정수 필드에서 **전법ID/무장ID** 추출.

- 장점: 코드 주입 없음, 읽기 전용 원칙 유지. 게임 버전 바뀌어도 재적용 가능.
- 난이도: 중상. 문자열 인코딩(UTF-16 vs UTF-8), 객체 헤더 오프셋, 32/64bit 포인터 판별 필요.

### 방안 B — IL2CPP 메타데이터 + global-metadata.dat 복원 (정밀, 리버싱)
`GameAssembly.dll` + 메모리상 복호화된 `global-metadata`를 Il2CppDumper류로 덤프하여 전법 테이블 클래스/필드 구조를 확정한 뒤, 그 스키마로 힙을 파싱.

- 장점: 가장 정확(필드명·타입 확정).
- 단점: 메타데이터 헤더 변형(암호화) 대응 필요. 시간 소요 큼. 이번 목표엔 과할 수 있음.

### 방안 C — UI 자동 순회 + OCR/문맥 캡처 (반자동 폴백)
게임에서 전법 목록을 자동/수동으로 한 화면씩 열며, 매 화면 캡처 시 이름+설명이 **함께** 메모리에 로드된 상태를 스냅샷 → 화면 단위로 이름·설명 인접 저장.

- 장점: 구조 리버싱 불필요, 가장 확실히 "이름+설명" 동시 확보.
- 단점: 완전 자동은 아님(전법을 하나씩 띄워야). 하지만 **A의 검증용 정답셋**으로 매우 유용.

> **추천 전략: A를 메인으로 하고, C를 소규모 정답셋(이미 확보한 유비/조운/장비/관우 등)으로 A의 매핑을 검증.** B는 A가 막힐 때만.

## 단계별 작업 (Phased Tasks)

### Phase 0 — 준비 & 정답셋 구축
- [ ] 게임에서 전법 목록/도감 화면을 열어 데이터가 메모리에 최대한 로드된 상태 확보.
- [ ] 관리자 권한 메모리 덤프 1회 수행(기존 `run_admin.ps1` 방식) → 원시 바이트 스냅샷 저장(문자열만이 아니라 **주소 정보 포함** 덤프 필요, Phase1 도구가 수행).
- [ ] 이미 확정된 전법을 **정답셋(golden set)** 으로 정리: 유비-백성과함께, 조운-칠진칠출, 장비-만인지적, 관우-화하진압/칠군수몰/기민한전술, S2 카드팩 13종 등.

### Phase 1 — 주소 보존 문자열 인덱서 (신규 도구: `mem_index.py`)
현재 스크립트는 문자열만 저장하고 **주소를 버린다**. 이를 개선:
- [ ] 커밋된 읽기가능 영역을 스캔하되, 각 문자열을 `(가상주소, 인코딩, 원본바이트, 디코드문자열)` 로 저장.
- [ ] **UTF-16LE**(IL2CPP 관리 문자열의 실제 저장형)도 스캔 대상에 추가. (현재는 UTF-8만)
- [ ] 산출물: `strings_index.jsonl` (주소·인코딩·텍스트), `regions.json`(영역 맵).
- [ ] 검증: 정답셋 문자열이 인덱스에 존재하고 주소가 잡히는지 확인.

### Phase 2 — 포인터 그래프 / 테이블 탐지 (`mem_pointers.py`)
- [ ] 후보 문자열들의 **객체 시작 주소** 계산(관리 문자열 헤더 오프셋 자동 추정: 이름/설명 문자열 앞 N바이트 스캔으로 length 필드 검출).
- [ ] 전체 메모리에서 **8바이트 정렬 포인터**를 스캔하여, 문자열 주소를 가리키는 슬롯 위치 수집.
- [ ] 포인터 슬롯들이 **일정 stride로 연속**한 구간 = 배열/구조체 테이블로 클러스터링.
- [ ] 산출물: `pointer_clusters.json` (테이블 후보: base, stride, count, 참조 문자열들).

### Phase 3 — 레코드 스키마 추론 & 이름↔설명 매핑 (`mem_schema.py`)
- [ ] 각 테이블 후보에서 **한 레코드 안에 이름-문자열 포인터와 설명-문자열 포인터가 함께** 오는 오프셋 패턴 탐색.
  - 이름 판별: 짧고(≤ ~12자) 전법명 사전과 매칭(정답셋 + `#ECCD7A`로 표기됐던 이름 목록).
  - 설명 판별: 길고 `giver.skillLv`/`<color=`/효과 키워드 포함.
- [ ] 같은 레코드의 정수 슬롯에서 **전법ID** 후보 추출(전투 로그의 `insSkill_<id>` 와 교차 검증).
- [ ] 무장 매핑: 무장↔전법 관계 테이블(또는 무장 링크 토큰 `<링크ID>_<슬롯>`)에서 **무장명 ↔ 전법ID** 연결.
- [ ] 산출물: `skill_map.json` — `{skillId, name, desc_raw, ownerGeneral?, isUnique?}`.
- [ ] 검증: 정답셋 전 항목이 스키마로 자동 복원되는지 대조(≥ 95% 일치 목표).

### Phase 4 — 수치 정제 & 상태 치환 (기존 `parse_skills.py` 확장)
- [ ] `skill_map.json`의 `desc_raw`에 대해:
  - `$base+giver.skillLv*step$` → **만렙(Lv10)** 계산, `%`면 ×100.
  - `giver.skillClass` 등 계산 불가 변수는 원본 유지.
  - `<color=>`, `<link=>`, `<br>` 등 마크업 제거.
  - `#N#` 상태 플레이스홀더 → 확정 매핑 치환(기존 STATE_MAP 재사용, 미확정은 원본 유지).
- [ ] 산출물: `skill_clean.json` — 정제된 최종 필드.

### Phase 5 — KB 파일 자동 생성 (`gen_kb.py`)
- [ ] 템플릿(현행 `유비-백성과함께.md` / `만인지적.md` 형식)으로 각 전법당 1파일 생성.
- [ ] 파일명 규칙: **`{무장}-{전법이름}.md`** (고유 전법), 일반 전법은 **`전법-{전법이름}.md`**.
  - 파일명 안전화: 공백/특수문자 처리, 중복 시 `-2` 등 suffix.
- [ ] 각 파일에 표(무장/이름/레벨/유형/특성), 만렙 설명, 수치 산출표, 핵심 정리, 출처·추출일 메타 포함.
- [ ] 인덱스 파일 `kb/_전법_인덱스.md` 자동 생성(무장별/유형별 목록 + 링크).
- [ ] `kb/_데이터출처_및_방법론.md`에 자동 매핑 방식·검증 결과 추가.

### Phase 6 — 검증 & 반복
- [ ] 정답셋 대조로 매핑 정확도 리포트 출력(불일치 목록 별도 파일).
- [ ] 게임 스크린샷 몇 건과 만렙 수치 교차검증(특히 `giver.skillClass` 포함/특수 전법).
- [ ] 누락 전법(메모리 미로드) 목록화 → 해당 화면을 게임에서 열고 재덤프 → 증분 병합.

## 리스크 / 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 관리 문자열이 UTF-16이라 현재 UTF-8 스캔에 안 잡힘 | 매핑 불가 | P1에서 UTF-16LE 스캔 추가(필수) |
| 이름/설명이 같은 구조체가 아니라 별도 dict(hash) 저장 | 오프셋 패턴 실패 | 포인터 역참조로 "같은 레코드"가 아니라 "같은 ID로 조회되는 두 테이블"을 ID 교집합으로 매핑(방안 A 확장) |
| 전법ID 정수 필드 식별 실패 | 무장 매핑 약화 | 전투 로그의 `insSkill_<id>` 토큰을 정답 앵커로 사용해 ID 위치 역추적 |
| 안티치트로 OpenProcess 거부 | 덤프 불가 | 관리자 권한 실행(기존 확인됨). 쓰기/후킹은 하지 않으므로 탐지 위험 낮음 |
| 게임 업데이트로 구조 변경 | 재작업 | 파이프라인화 + 정답셋 회귀 검증으로 빠른 재적용 |
| 일부 전법이 메모리 미로드 | 누락 | 도감/목록 화면 순회로 로드 유도 후 증분 덤프·병합 |

## 예상 난이도 & 순서 제안

1. **P1(주소+UTF-16 인덱서)** 부터 시작 — 여기서 이름/설명 문자열의 실제 인코딩·주소가 확정되어야 이후 단계가 성립. (가장 먼저, 리스크 최대 요소 제거)
2. P2 포인터 클러스터 → P3 매핑을 정답셋으로 검증하며 반복.
3. 매핑이 서면 P4/P5는 기존 `parse_skills.py`와 템플릿 재사용이라 비교적 빠름.

> 다음 액션으로 무엇부터 구현할지 (예: **P1 `mem_index.py`** 부터) 지시해 주시면 그 단계 코드를 작성하고 게임 실행 상태에서 검증하겠습니다.

# 진행 로그 (실측 결과)

## Phase 1 (완료) — 주소 보존 인덱서
- `tools/mem_index.py` 작성/실행. 결과: UTF-8 84,685 / **UTF-16LE 1,508,765** 문자열.
- 관리 문자열 대부분 UTF-16LE이나, **전법 이름·설명 본문은 UTF-8**. 문자열 객체 시작 = 본문주소 - 0x18 (문자열 앞 -4에 UTF-8 바이트길이 필드).

## Phase 2/3 (Plan A) — 포인터 구조 매핑 → **실패/보류**
- `mem_ptr_probe.py`/`mem_pair.py`/`mem_tables.py`/`mem_dissect.py` 로 검증.
- 결론: 이름/설명 포인터가 **배열(SoA)도, 공통 레코드 구조체도 아님**. 골든셋(백성과함께)의 name/desc 포인터가 2.3MB 떨어져 있고 고정 stride 클러스터 없음. 로컬 키 문자열도 없음.
- → 순수 포인터 인접성으로는 자동 매핑 불가. **Plan B 필요** 확정.

### 메모리에서 복호화본 발견·덤프 성공 ★
- `md_find.py`: magic 2건. `0x27d1fd30000`=원본(암호화), **`0x27d21188040`=복호화본**(오프셋 테이블이 정상: 0x100, 0x451c0, 0x452c0, 0xc5880, ...). version 필드만 여전히 변형.
- `md_dump.py`: `0x27d21188040`에서 21,274,200바이트 전체 덤프 → `extracted/auto_pipeline/global-metadata.dec.dat`.
- `md_parse.py`: 헤더 파싱 성공, ASCII 문자열 풀 위치 확인(hdr[7]=0x26723c, hdr[41]=0x1c75c8 등). C# 네임스페이스/타입명 평문 판독 가능(`NSLGame.*`, `NSLGScene.*`, `XLua.*`, `NEP` 등).

### 중대한 발견: 게임은 **XLua 기반**
- 문자열 풀에 `XLua.CSObjectWrap|GameConfigWrap`, `GameConfig`, `luascripts.ns`, `lua-patches` 폴더 존재.
- → **전법/무장 수치·텍스트 상당수가 C# 필드가 아니라 Lua 테이블에 있을 가능성이 큼.** 그렇다면 IL2CPP 필드 파싱보다 **Lua 테이블 추출**이 더 정확·자동화 용이.

# Plan B 확정 결과 (B-IL2CPP 배제, B-Lua 확정)

## B-IL2CPP 배제 근거

## 디스크 Lua 번들도 암호화
- `lua_probe.py`: `luascripts.ns` = UnityFS 컨테이너(정상) + 내부 SerializedFile **version 문자열 깨짐(payload 암호화)**. → 메모리에서 추출 필요.

## Lua 메모리 구조 확정 (핵심)
- `lua_find.py`: '백성과 함께' 이름 5곳, 설명 1곳. 이름/설명이 `0x27eb0...` 아레나(Lua 문자열 힙)에 존재.
- `lua_arena.py`/`lua_node.py`: 설명 문자열은 **Lua 5.3/5.4 TString**. 레이아웃 확정:
  - **객체 시작 = 본문주소 - 0x18**
  - 헤더: `tt=0x04(LUA_TSTRING)`, hash(4B), len(4B, body-4), 이후 UTF-8 본문.
- 설명 TString 을 가리키는 포인터는 **`0x7ff4...` 영역에 1개** (slot=0x7ff4b0514740). 그 주변은 **8바이트 포인터들의 배열(0x27e... 힙 포인터 다수)** = **Lua 테이블의 노드/배열부** 또는 C# 측 ref 배열.
- 즉 전법 레코드 테이블은 `0x7ff4...` 영역. 이름/설명이 서로 다른 컬럼(수백KB~MB 떨어짐)이라 Plan A 단순 인접 매핑이 실패했던 것.

## 다음: 통합 추출기 (B-Lua-2 축약형)
1. 모든 이름후보/설명후보 TString 의 '객체시작주소(body-0x18)'→텍스트 맵 구성.
2. `0x7ff4...` 테이블 영역에서 이 TString 들을 가리키는 포인터 슬롯 전수 수집.
3. 테이블 노드 stride 로 이름-컬럼/설명-컬럼을 레코드 인덱스로 정렬·페어링.
4. 검증: 백성과함께(name slot 0x7ff4b07523d0 / desc slot 0x7ff4b0514740)가 같은 레코드로 묶이는지.

# Plan B 최종 결론 (완전 자동화 = 현 제약 하에서 불가)

## 추가 실측 (B-Lua 심화)
- `lua_walk.py`: 골든 desc 문자열을 값으로 갖는 위치는 **오직 `0x7ff4...` XLua ObjectTranslator 풀 1곳**. Lua 노드 아님.
- `lua_parent.py`: **이름 포인터와 설명 포인터가 메모리 어디에서도 512B 이내로 공존하지 않음** → 이름·설명을 잇는 공통 부모 객체 없음.
- `lua_dict.py`: 문자열 객체(시작=body-0x18)를 가리키는 포인터는 전 메모리에 **3개뿐(전부 0x7ff4 풀)**, **인접 정수 skillId 없음**, C# Dictionary Entry 아님.

## 근본 원인 (확정)
전법 **이름/설명은 메모리에 독립 문자열 객체로만 존재**하고, **XLua ObjectTranslator 풀의 불투명한 정수 ref-ID로만 참조**됨. 이름·설명·ID를 함께 담는 지속 구조(C# 클래스/Dictionary/Lua Table)가 **존재하지 않음**. 조인은 렌더 시점 Lua 함수의 지역변수에서 일시적으로만 일어나고 보존되지 않음.

## 결론
- **읽기 전용 + 무주입** 원칙 하에서는 **오프라인 완전 자동 매핑 불가**.
- 자동 조인하려면 (a) 렌더 함수 후킹 또는 (b) 라이브 VM 계측이 필요 → 안티치트(NEP2) 및 안전 원칙 위반.

## 성과로 남는 것 (재사용 가능)
- 메모리에서 **복호화 global-metadata 덤프** 성공(`global-metadata.dec.dat`) + 자체 파서(`md_ident.py`)로 타입/필드 판독 가능.
- **UTF-16 포함 전체 문자열 인덱스**(`strings_index.jsonl`) + 주소 보존.
- 전법 설명 421개 + 이름 목록 확보.

## 현실적 대안 (권장): 트랙1 반자동 순회 캡처
- 게임에서 전법을 순서대로 열 때마다 스냅샷 → '직전에 연 이름' + '새로 나타난 desc' 를 시점 기반으로 자동 매칭.
- 이름·설명이 같은 화면에 동시 로드되는 유일한 순간을 활용 → 조인 성립.
- 완전 무인은 아니지만(전법을 넘겨야 함), 안전 원칙 준수 + 전 전법 커버 가능.
